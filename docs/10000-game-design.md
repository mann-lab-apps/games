# 10000 게임 기획

## 한 줄 설명

`10 x 10` 숫자 보드 안에서 가로 또는 세로로 숨어 있는 `10000`을 빠르게 찾아 누르는 하이퍼 캐주얼 게임.

## 핵심 재미

플레이어가 느껴야 하는 감정은 "봤다!", "찾았다!", "바로 다음!"이다.

복잡한 조작보다 순간 인지, 시선 스캔, 빠른 판단이 핵심이다. 한 판은 짧고, 실패해도 바로 다시 하고 싶어야 한다.

## 기본 루프

1. 보드가 열린다.
2. 플레이어가 `10000`을 찾는다.
3. 정답 위치를 누른다.
4. 맞으면 남은 시간을 유지한 채 즉시 다음 스테이지로 넘어간다.
5. 전체 런 제한 시간이 끝나면 런이 종료된다.
6. 기록은 제한 시간 안에 클리어한 스테이지 수로 남는다.

## 보드 규칙

- 시작 보드는 `10 x 10`.
- 각 칸은 `0`부터 `9`까지의 한 자리 숫자.
- 모든 스테이지에는 최소 1개의 `10000`이 반드시 들어간다.
- MVP에서는 오른쪽 방향, 아래 방향만 사용한다.
- 역방향은 나중에 난이도가 너무 낮을 때 추가한다.

가능한 방향:

- 가로 왼쪽에서 오른쪽: MVP 포함
- 세로 위에서 아래: MVP 포함
- 가로 오른쪽에서 왼쪽: 추후 후보
- 세로 아래에서 위: 추후 후보

## 조작 방식

MVP 추천:

- `10000`을 이루는 다섯 칸 중 아무 칸이나 누르면 정답 처리.

나중에 검토:

- 다섯 칸을 드래그해서 선택해야 정답 처리.

첫 버전은 탭 방식이 좋다. 드래그는 발견감은 좋지만 속도를 늦추고, 작은 화면에서 오입력이 늘어날 수 있다.

## 난이도 설계

MVP 난이도는 보드 크기와 입력 규칙을 고정하고, 한 판 전체 제한 시간 안에서 몇 스테이지를 클리어하는지로 만든다. 스테이지마다 시간이 리셋되면 한 판의 긴장감이 끊기므로, 타이머는 전체 런 동안 계속 흐른다.

| 구간 | 보드 | 전체 런 시간 | 방향 | 의도 |
| --- | --- | --- | --- | --- |
| MVP | 10 x 10 | 60.0초 | 오른쪽, 아래 | 제한 시간 안에 최대한 많은 스테이지 클리어 |
| 이후 후보 | 10 x 10 | 45-60초 | 오른쪽, 아래, 역방향 후보 | 지표 기반 압축 |

사용자가 말한 "갈수록 주어지는 숫자가 짧게"는 MVP에서는 적용하지 않는다. 첫 배포 후보는 전체 60초 안에서 얼마나 많은 보드를 넘기는지에 집중한다. 숫자 자체를 짧게 보여줬다가 가리는 기억력 모드는 나중에 별도 모드로 검토한다.

## 생성 규칙

1. `10 x 10` 보드를 랜덤 숫자로 채운다.
2. 유효한 시작 칸과 방향을 고른다.
3. 해당 위치에 `1`, `0`, `0`, `0`, `0`을 덮어쓴다.
4. 우연히 생긴 다른 `10000`도 정답으로 인정한다.

MVP에서는 여러 정답을 허용한다. 경쟁 모드나 랭킹을 붙일 때는 정확히 하나만 생성되도록 검사한다.

## 점수와 기록

핵심 점수:

- 클리어한 스테이지 수

보조 기록:

- 최고 스테이지
- 평균 클리어 시간
- 가장 빠른 클리어
- 오답 횟수
- 연속 정답 수

랭킹 기준 후보:

```txt
1순위: 클리어 스테이지 수
2순위: 총 클리어 시간
```

## 실패 조건

MVP 추천:

- 전체 런 시간이 끝나면 런 종료.
- 오답 탭은 즉시 실패가 아니라 `0.5초` 시간 페널티.

즉시 실패보다 시간 페널티가 좋다. 작은 폰 화면에서 손가락 오입력이 날 수 있고, 하이퍼 캐주얼 게임에서는 흐름이 끊기는 것보다 압박이 커지는 편이 낫다.

## 화면 구성

게임 화면:

- 시작 오프닝: `1 / 0 / 0 / 0 / 0` 타일이 잠깐 나타났다가 사라지며 찾아야 할 패턴을 보여준다.
- 상단: 현재 스테이지, 최고 기록, 타이머 바
- 중앙: 정사각형 숫자 보드
- 하단: 최소 여백 또는 작은 일시정지 버튼

결과 화면:

- 도달 스테이지
- 최고 기록
- 다시하기 버튼
- MVP에서는 광고/부활 버튼 제외

플레이 중 설명 문구는 최소화한다. 보드가 곧 게임이어야 한다.

## 디자인 적용

Mann Lab Games 공통 비주얼 기준인 손그림 스케치 스타일을 따른다.

참조:

- `docs/visual-direction.md`

`10000`에서 특히 중요한 점:

- 칸은 완벽한 직선 격자보다 살짝 흔들린 라인으로 표현한다.
- 숫자는 손글씨 느낌을 검토하되, 판독 속도를 해치면 안 된다.
- 타이머 바는 손으로 그은 밑줄처럼 보이게 한다.
- 정답 `10000`은 찾기 전에는 다른 숫자와 같은 스타일이어야 한다.

## 피드백

정답:

- `10000` 칸 위에 형광펜을 그은 듯 짧게 강조된다.
- 150-250ms 안에 다음 보드로 넘어간다.
- 짧은 상승 사운드.

오답:

- 누른 칸에 붉은 펜 체크 또는 흔들림이 들어간다.
- 타이머 바가 짧게 흔들리거나 붉게 반응한다.
- `0.5초` 차감.

시간 종료:

- 보드가 어두워진다.
- 정답 위치가 드러난다.
- 결과 화면으로 빠르게 전환된다.

## MVP 범위

첫 구현에 포함:

- 시작 오프닝 목표 타일 모션
- `10 x 10` 보드
- 매 스테이지 최소 1개의 `10000`
- 오른쪽/아래 방향
- 정답 칸 탭으로 클리어
- 전체 런 제한 시간
- 오답 시간 페널티
- 결과 화면
- 로컬 최고 기록 저장
- 다시하기

첫 구현에서 제외:

- 광고
- 온라인 랭킹
- 스킨
- 역방향
- 데일리 챌린지
- 튜토리얼 화면

## MVP 이후 작업 순서

1. 분석 이벤트 정의
2. Firebase Analytics / GA4 후보 검토
3. Crashlytics 후보 검토
4. Google AdMob 광고 위치 검토
5. Google Ads 유입 캠페인 준비 여부 검토
6. Android 내부 테스트 빌드 업로드
7. 지표 기반 난이도 조정

MVP가 플레이 가능해지기 전에는 분석 SDK와 광고 SDK를 붙이지 않는다. 먼저 게임이 다시 하고 싶은지 확인한다.

## 분석 이벤트 후보

SDK는 아직 붙이지 않는다. MVP 플레이 검증 뒤 아래 이벤트를 기준으로 Firebase Analytics / GA4 적용을 검토한다.

| 이벤트 | 발생 조건 | 주요 파라미터 | 알고 싶은 것 |
| --- | --- | --- | --- |
| `run_start` | 새 런 시작 | `best_cleared_stages` | 다시 시작 흐름이 자연스러운가 |
| `stage_clear` | 정답 탭으로 스테이지 클리어 | `stage`, `run_time_limit`, `remaining_time`, `wrong_taps`, `target_count` | 어느 구간이 너무 쉽거나 어려운가 |
| `wrong_tap` | 오답 칸 탭 | `stage`, `remaining_time`, `penalty` | 오입력이 많은 구간이 있는가 |
| `run_end` | 시간 종료 | `cleared_stages`, `failed_stage`, `run_duration`, `wrong_taps` | 평균 도달 지점과 런 길이는 적절한가 |
| `restart` | 결과 화면에서 다시하기 | `previous_cleared_stages`, `best_cleared_stages` | 한 판이 다음 판으로 이어지는가 |
| `app_open` | 앱 실행 | `best_cleared_stages` | 재방문이 있는가 |

## 성공 기준

프로토타입을 계속 밀어볼 만한 기준:

- 처음 잡은 사람이 5초 안에 목표를 이해한다.
- 한 판이 끝나면 바로 다시 하게 된다.
- 스테이지 10은 쉽게 도달한다.
- 스테이지 25는 꽤 잘한 느낌이 든다.
- 오답이 억울하지 않다.
- 실제 Android 폰에서 보드가 충분히 잘 읽힌다.
